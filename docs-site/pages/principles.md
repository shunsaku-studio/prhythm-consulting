# 設計原則

## 1. 共通の出力は最小限にする

どのスキルも、**本体**（図表）、**出典タグ付きのファクト**、**前提と未確認事項**の 3 点を返す。「示唆」や「次の問い」の欄は必須にしない。形式として欄を設けると、もっともらしい文で埋まるだけだからだ。示唆は、質問タイムで人が問う。

## 2. 中計と経営者を起点にし、二本のレーンで提案する

顧客の中計は、尊重して翻訳する対象であり、否定する対象ではない。そのうえで、提案は二本のレーンで組む。

| レーン | 中身 |
|--------|------|
| レーン 1：中計に則る | 「目標に届くには、これだけの打ち手が要る」と必要量を示す |
| レーン 2：中計の外側 | ベースレートや資本の制約から見た、別の道筋を置く |

どちらを前に出すかは、マネージャーがゲートで決める。

## 3. 数字は会話の中で計算しない

年率換算、ブリッジ、感応度は、`scripts/` 配下のスクリプトか Excel の数式で計算する。事業計画モデルは、セルに数値を直打ちしない構成にする。

## 4. すべての数字に出典タグを付け、分からない値は空欄で残す

| タグ | 意味 |
|------|------|
| 公開 | 公開情報から取った値 |
| クライアント提供 | 社内資料から取った値 |
| 推定 | 根拠と計算式が示せる値 |
| 仮置き | 議論のために置いた根拠のない値。差し替えの期限を付ける |

もっともらしい推定で埋めるより、— で残すことを優先する。出典タグのない数字は、デッキに載せない。

## 5. 人が決める場所を明示する

目標の解釈、検証する仮説の優先順位、追う打ち手、確度の置き方、どちらのレーンを前に出すか、撤退基準は人間が決める。スキルは比較表と論点を揃えるところまでにとどめ、決定は意思決定ログ（D）に残す。

## 6. ひとりで回してよい範囲を示す

各スキルに「単独度」を付ける。

| 記号 | 意味 |
|:----:|------|
| ◎ | ひとりで完結 |
| ○ | 結果をレビューに出す前提 |
| △ | 上位者と一緒に決める |

## 7. 学習の仕組みはスキルに入れない

スキルは、作業を速く正確にすることだけに集中する。理解度クイズや自己レビューの強制のような学習用の手順は、スキルに入れない。忙しいときに飛ばされるからだ。理解の確認は、スキルの外の[先輩質問タイム](/guide/question-time/)で行う。

## 8. 作らなくてよいものは作らない

事例調査、チャート選び、議事録のまとめは、汎用の LLM で足りるので作らない。成果物の示唆を引き出す so-what や、マネージャー目線の self-review も作らない。その役割は先輩質問タイムが担う。スライドの作成も、別の道具に任せる。

PEST、ファイブフォース、SWOT、3C、バリューチェーンの定番フレームワークは、スキルとして置く。汎用の LLM でも枠は埋まる。それでもスキルにするのは、ジュニアに「その道具がある」と知ってもらうためだ。あわせて、枠を埋めて終わらないための作法（問いから始める、事実に ID を付ける、優先順位を付けて次のスキルに渡す）を一緒に渡す。使い分けは[フレームワークの使い分け](/guide/frameworks/)にまとめた。

## 9. 二つのモードで同じ成果物を育てる

| モード | 中身 |
|--------|------|
| アウトサイドイン（提案前） | 公開情報だけで、1〜2 週間で提案の骨子とビジネスケースの仮説を作る。最初のリリースはこちらに集中する |
| インサイドアウト（受注後） | クライアントから提供された社内データで、同じ成果物を差分で更新しながら精緻化する |

作り直しはしない。社内データは案件フォルダの `client/` に置き、Web 検索のクエリに使わない。台帳の `confidentiality` 列でクライアント提供の値を区別し、社外に出す成果物から外す。
