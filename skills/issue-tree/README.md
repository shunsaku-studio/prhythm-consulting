# issue-tree

## 概要

目標の仕様（00-target-spec.md）と依頼文を渡すと、答えるべき問いを論点ツリー（Q-xxx）に分け、論点ごとに検証できる仮説（A-xxx）を置いて返す。重なりと漏れの点検（MECE）と、検証の優先順位の案も付ける。優先順位を決めるのは人である。

## 利用メリット

- 2 週間で何を分析するかが、論点の形で決まる。
- 仮説ごとに「どのデータで否定されるか」を書くので、分析が答えに向かう。
- 漏れと重なりを点検してから作業に入れる。

## 利用シーン

- 目標の解釈を合意した直後（お題A の 2〜3 日目）
- 依頼が抽象的で、何に答えればよいかが揃っていないとき
- 新規参入の可否を問われ、論点を切り分けたいとき（お題C）

依頼の例: 「論点出して」「何に答えればいいか整理して」「仮説立てて」

## 使い方

target-math で 00-target-spec.md ができた後、workplan の前に入る。

1. 依頼文と目標の仕様を渡す。経営者の公の発言（leadership.md）があれば一緒に渡す。
2. スキルが一番上の問いを一文にし、3〜5 個の論点に分ける。
3. 論点ごとに、データで確かめられる仮説を置く。仮説を否定するデータも書く。
4. スキルが MECE を点検し、優先順位の案を付けて `01-issue-tree.md` を書く。
5. スキルは止まり、検証する仮説の優先順位をマネージャーに決めてもらう。

## 人が決めること

- 検証する仮説と、その順番（このゲートで決め、decisions.md に残す）
- 外す論点（取り下げた論点も番号を残す）

## よく外す点

- 仮説が「成長の余地がある」のように、否定しようのない文になっている
- 論点が網羅的すぎて 2 週間で終わらない。または答えを左右しない論点が混ざる
- 使う予定のないフレームワーク（PEST、SWOT など）を埋める
- 優先順位をスキルが決めてしまう

詳しくは [references/pitfalls.md](references/pitfalls.md)。

## 具体例

| 論点 | 問い | 仮説 |
|---|---|---|
| Q-001 | どこにいくら足りないか | A-001 成り行きは市場成長並みで、FY2030 のギャップの大半はシェア獲得では埋まらない |
| Q-003 | 打ち手の投資を資本で手当てできるか | A-003 ネット D/E 0.5 倍 [F-056] の下では、FY2030 までの大型買収は 1 件が限度 |
| Q-005 | どれも当てはまらないなら | A-005 FY2030 は資本規律の中で届かないが、FY2033 なら買収を 2 段に分けて届く |

優先順位は A-001 → A-003 → A-002 → A-005 と決めた（D-003）。
