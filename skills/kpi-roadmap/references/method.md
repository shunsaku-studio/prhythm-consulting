# method — 手順と、なぜその順か

## 1. 年度別の KPI 目標をモデルから取る

売上、営業利益率、ROIC の年次の値は `model/model.csv` から取る。会話で按分したり、きりのよい数字に丸めたりしない。モデルの値は `推定` で、`source` にモデルの F- の ID を書く。

施策ごとの先行指標（受注、稼働率、顧客数など）は KPI ツリーから 1〜2 個だけ選ぶ。全部の KPI を年度別に並べると、どれで判断するのかが見えなくなる。

KPI × 年度ごとに一つの K- を振る（`--assign-ids`）。台帳は 1 つの ID に 1 つの値しか持てないからだ。

## 2. 矢羽は年単位で引く

一行が一つの施策、一列が一つの年度。フェーズは `【フェーズ】` で始まり、`━━━` で続き、`━━▶` で終わる。ゲートは `◆G1` でその年度のセルに入る。

月単位にしないのは、提案の段では月単位の精度がないからだ。月単位の計画は、受注後に実行計画として作る。

## 3. ゲートは取り返しのつかない約束の直前に置く

大きな設備の発注、買収の契約、新市場への参入。こうした約束の前にゲートを置く。約束の後のゲートは、やめても費用が戻らない。

ゲートの指標は感応度の上位から選ぶ。答えを一番動かす前提を、一番早く確かめるためだ。

## 4. 判定基準を全部書く

一つのゲートに、次の 6 つがそろって初めて判定できる。

| 欄 | 欠けるとどうなるか |
|----|-------------------|
| 指標 | 何を見るかで揉める |
| 閾値（K-） | 結果が出てから線を引くことになり、続ける側の結論に偏る |
| 期日 | 判断が先送りされる |
| データの出どころ | その日に数字がなく、判定できない |
| Go のとき | 通っても何も始まらない |
| 撤退基準 | 届かなくても続ける |

スクリプトは、指標・閾値・期日・データの出どころ・撤退基準の欠けをエラーにする。閾値が台帳の K- の値と違えばエラーにする。

## 5. 人と決める

閾値と撤退基準は、スキルが決めない。案と根拠（モデルの値、感応度、ベースレート）を並べ、マネージャーと決める。決まったら `decisions.md` に D- を残し、`gates.csv` に D- を書き、閾値の台帳の行を仮置きから決めた値に直す。

## なぜこの順か

目標 → 矢羽 → ゲート の順にすると、ゲートが「どの目標の、どの前提を確かめるか」とつながる。先にゲートを書くと、確かめやすいものを確かめるゲートになりやすい。
