# pitfalls — よく外す点

## 1. 子を足しても親にならない

悪い例: 成り行きのセグメント合計（セグメント情報）と、連結の成り行き（全社の成長率で計算）を同じツリーに並べる。調整額の分だけ合わない。

良い例: どちらの定義で切るかを決め、合わない分を「調整額」のノードとして置くか、前提と未確認事項に書く。

## 2. 会話の中で掛け算・割り算をして埋める

悪い例: 「数量 × 単価」を会話で計算して、セグメント売上のノードに書く。

良い例: 値は台帳か `model/model.csv` から取る。なければ、その値を作るスキルのスクリプトで計算するか、— のまま残す。

## 3. 公開情報で分からないノードを、もっともらしい推定で埋める

悪い例: 単価を「業界平均で 1 個 ○ 円」と根拠なく置く。

良い例: — のまま残し、インサイドアウトで取るデータとして書く。

## 4. 会社が動かせないノードを KPI にする

悪い例: 「市場成長率」を管理する KPI にする。

良い例: 市場成長は前提として持ち、会社が動かせるもの（受注、シェア、稼働率、単価）を KPI にする。

## 5. ROIC を売上のツリーだけで説明する

悪い例: 売上が伸びれば ROIC も上がる、とだけ書く。

良い例: NOPAT マージンと投下資本回転率に分け、M&A ののれんや設備投資が回転率を下げることを見せる。

## 6. 定義の違う ID を二重に登録する

悪い例: すでに S-001 で載っている成り行き売上を、K-010 として台帳に足す。

良い例: 既存の S-・G-・I-・F- はその ID のまま使う。K- は新しいノードにだけ振る。
