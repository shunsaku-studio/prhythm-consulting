# method — 手順と、なぜその順か

## 1. 台帳から直す

レポートのエラーは、台帳（`facts.csv:行番号`）のものから先に直す。

なぜ: 台帳の行が壊れていると、その ID を使うすべての成果物が連鎖してエラーになる。台帳を直すと、下流のエラーの多くが消える。

台帳のエラーの直し方:

| エラー | 直し方 |
|--------|--------|
| 出典タグが 4 種のいずれでもない | 公開 / クライアント提供 / 推定 / 仮置き のどれかに直す。迷ったら仮置きにし、`replace_by` を入れる |
| 公開の値に資料名がない | 資料名とページを入れる。見つからなければ仮置きに落とす |
| 推定の値に計算式がない | 計算したスクリプトと入力 ID を書く。式が書けないなら推定ではない |
| 計算式が参照する ID がない | 参照先を台帳に足すか、式の ID の打ち間違いを直す |
| 仮置きの期限切れ | 人に聞く（SKILL.md の停止点） |
| クライアント提供が社外秘でない | `confidentiality=社外秘` にする。値を `client/` に置いているかも確かめる |

## 2. 成果物のエラーを 4 つに振り分ける

| 振り分け | 当てはまるとき | 直し方 |
|---------|--------------|--------|
| ID を付ける | 値は正しく、ID だけがない | 数字の直後に `[ID]` を書く |
| ファイルを直す | ファイルが古い値を載せている | 台帳の値に合わせる |
| 台帳を直す | 台帳の値が古い（差し替え漏れ） | 値を作ったスキルのスクリプトを回し直し、台帳を更新する |
| `—` にする | 出典がどこにもない | `—` にし、前提と未確認事項に書く |

なぜ「ファイルを直す」が「台帳を直す」より先か: 台帳が正本だからだ。エラーを消すために台帳を書き換えると、正本が崩れる。台帳を直すのは、台帳の値が古いと確かめたときだけにする。

## 3. 警告を見る

作業ファイルの警告は、その数字がいずれ `deliverables/` に載るかで判断する。載るなら今 ID を付ける。載らないなら残してよい。

`deliverables (S-001) | 仮置きか — に依存しています` の警告は、成果物の数字が根の深いところで仮置きに支えられていることを示す。直すのではなく、デッキの注記で「仮置きを含む」と示すか、仮置きを差し替える。どちらにするかは人が決める。

## 4. --strict で最終点検

最終メッセージを確定する前に `--strict` で回す。警告もエラーになるので、残っている仮置き依存がすべて見える。0 件にできないときは、残る理由を `reviews/number-audit-triage.md` に書いて上に出す。

## 5. モデル（xlsx）のエラー

- `inputs シートがありません` — business-case-model の型（CONVENTIONS 3 節）に合っていない。モデルを作り直す側の作業になる。
- `数式のない数値セル（直打ち）` — 計算シートに値が直接打たれている。inputs シートに行を足し、そのセルを参照する式に直す。1 行目は年度などの見出しとみなして見ない。年度を 2 行目以降に置くなら文字列にする。

## なぜスクリプトで点検するか

人の目で数字を突き合わせると、見たいものしか見えない。とくに自分が作った成果物では、正しいと思い込んだ数字を飛ばす。スクリプトは全部の数字を同じ規則で見る。人は、スクリプトが見ないこと（定義の違い、妥当性）に時間を使う。
