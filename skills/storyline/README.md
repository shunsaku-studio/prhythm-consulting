# storyline

## 概要

分析を終えた案件フォルダを渡すと、結論から始まるストーリーラインを返す。中身は、一文の統治メッセージ、ピラミッド（主張 → 根拠 3 つ前後 → 根拠ごとの ID 付きの事実）、見出しだけのゴーストデッキの 3 つだ。これを二本のレーンで書く。レーン1 は中計に則り「目標に届くにはこれだけの打ち手が要る」を示す。レーン2 はベースレートや資本の制約から見た、中計の外側の道筋を示す。どちらを前に出すかはマネージャーが決める。出力は `deliverables/storyline.md`。スライドは作らない。

## 利用メリット

- 分析した順ではなく、結論から並んだ骨子が先にできる。スライドを作る前に、言いたいことが一文で言えるかを確かめられる。
- すべての見出しに ID が付くので、どのページがどの事実に依っているかを、ページを作る前にたどれる。
- 二本のレーンを並べるので、「中計どおりに頑張る」案と「中計の外側を考える」案を同じ土俵で比べられる。

## 利用シーン

- 分析が一通り揃い、経営会議に何を持っていくかを決める段（お題A の 10 段目）
- 途中で、今の分析からどんなメッセージが言えるかを試すとき。言えなければ、どこが足りないかが見える

依頼の例: 「ストーリーにして」「ゴーストデッキ作って」「結論から組み立てて」「経営会議向けの骨子作って」

## 使い方

**いつ使うか:** gap-bridge、initiative-sizing、capital-capacity、kpi-roadmap の後。書いたら number-audit で数字を点検する。スライドは別のツールで作る。

1. 案件フォルダを渡す。スキルは、聞き手、答える問い、決まっている意思決定（目標の解釈など）を確かめる。目標の解釈が決まっていなければ止まる。
2. スキルがレーン1 とレーン2 の「一言で」を書き、それぞれのピラミッドとゴーストデッキを組む。数字は台帳にあるものだけを ID 付きで使う。ないものは `—` にして未確認事項に回す。
3. 構成を点検する。

   ```bash
   python3 skills/storyline/scripts/outline_check.py cases/hokushin/deliverables/storyline.md
   ```

4. 数字を点検する（number-audit）。`deliverables/` のエラーを 0 件にする。
5. スキルが二本のレーンを並べて止まる。マネージャーがどちらを前に出すかを決める。決定は `decisions.md` に D- で残す。
6. スキルが統治メッセージを書き、前に出すレーンを先に並べ替える。`outline_check.py --final` と number-audit の `--strict` でもう一度点検する。

## 人が決めること

- どちらのレーンを前に出すか
- 最終の統治メッセージ（一文）
- 根拠の足りない主張を、外すか、分析に戻って埋めるか

スキルはレーンを選ばない。聞かれれば理由を添えて意見を言うが、決めるのはマネージャーだ。

## よく外す点

- 分析した順に並べ、結論が最後に来る。1 ページ目が「前中計の振り返り」で始まり、最後に「まとめ」が来る。
- 見出しが「市場概要」「打ち手の比較」のようなトピックラベルになり、何を言いたいのかが分からない。
- レーン2 を「目標は無理」と言うためのレーンにする。赤旗は、M&A や市場の選び直しという別の道筋の根拠である。
- ストーリーに合わせて数字を足す。台帳にない数字を、会話の中で作って見出しに入れる。

詳しくは [references/pitfalls.md](references/pitfalls.md)。
